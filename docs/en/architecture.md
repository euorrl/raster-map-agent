# Project Architecture

中文版: [项目架构](../architecture.md)

This document records the current V1 code structure, workflow architecture, and main node responsibilities. Based on the current implementation, V1 is a controlled workflow agent rather than an agent that lets the LLM freely call low-level tools.

## Overall Positioning

Raster Map Agent is currently a locally runnable end-to-end Sentinel-2 raster map generation agent.

Core principles:

```text
planner understands what the user wants
registry resolves the parameters required by a product
compiler compiles the plan into controlled tool calls
executor executes tool calls one step at a time
validator / adjuster perform post-tool quality checks and limited retries
tools perform deterministic remote-sensing data processing
```

## AgentState

`AgentState` is the shared state object in the workflow. Its main fields include:

- `user_query`: the original user request;
- `plan`: the structured task plan generated by the planner;
- `tool_calls`: the controlled tool call list generated by the compiler;
- `workspace`: workspace information for the current task;
- `tool_results`: results from each tool;
- `runtime`: runtime information for planner, registry, compiler, executor, validator, adjuster, and related control logic;
- `final_answer`: the final answer;
- `status`: current workflow status;
- `errors` / `warnings`: append-only errors and warnings.

`plan`, `workspace`, `tool_results`, and `runtime` use recursive merge semantics, so each node only needs to return partial updates.

## Current Workflow

The current high-level flow is:

```text
planner
-> route decision
-> registry if raster task
-> compiler
-> execute_tool loop
-> optional validate_tool / adjust_tool loop
-> final answer
```

`workflow.py` provides the LangGraph graph. When LangGraph is unavailable, `_LinearWorkflow` acts as a fallback runner and simulates the same execution order.

## Node Responsibilities

### planner_node

`planner_node` calls the planner, parses the user's natural-language request, generates `state.plan`, and decides the route.

Current routes:

- `raster_product_generate`: supported raster map generation tasks;
- `direct_answer`: general questions, system capability questions, and currently unsupported product requests.

The planner only generates a structured plan. It does not generate `tool_calls`, determine low-level tool order, band roles, index formulas, validators, or retry parameters. Planner runtime information is written to `runtime["planners"]["global"]`.

### registry_node

`registry_node` is used only by the raster route. It resolves raster product configuration from `state.plan["index_name"]` and the data source, then writes it to:

```python
runtime["registry"]["raster_product"]
```

Real raster preparation currently uses only Sentinel-2. The registry includes basic Landsat configuration, but V1 does not expose Landsat as a real executable pipeline.

### compiler_node

`compiler_node` compiles `state.plan`, registry configuration, and the workflow template into standard `tool_calls`, then initializes `runtime.current_tool_index`.

This design:

- prevents the LLM from freely deciding low-level tool parameters;
- fixes tool order in the workflow template;
- lets the executor resolve dependencies at runtime through `$state...` references.

### tool_executor_node

`tool_executor_node` executes one tool call at a time. It reads:

```python
runtime["current_tool_index"]
```

Then it executes `tool_calls[current_tool_index]`, writes results to `workspace`, `tool_results`, or `final_answer`, and advances `current_tool_index` to the next tool.

The executor also records:

- `runtime.last_tool_index`
- `runtime.last_tool_call_id`
- `runtime.last_tool_name`

These fields are used by later validator / adjuster routing.

### tool_validator_node

This node first checks whether the just-completed `tool_call_id` has a tool rule in `tool_rules`. If a rule exists, the workflow enters validation. Currently, only `raster_prepare` has a tool rule.

The `raster_prepare` validator mainly checks:

- whether a raster prepare result exists;
- required bands from the registry or prepare result;
- whether diagnostics exist;
- whether coverage meets the requirement;
- whether required band paths exist.

The validator only returns `passed`, `retryable`, or `failed`. It does not modify tool call parameters or execute tools.

### tool_adjuster_node

When the validator returns a retryable result, the adjuster first reads the retry count from `state.runtime["retry_counts"][tool_call_id]` to check whether the threshold has been reached. If not, it uses the `tool_call_id` to find the corresponding rule in `tool_rules` and enters the adjuster.

The current `raster_prepare` adjuster:

- adjusts allowed fields based on validator suggested actions;
- can adjust `start_date`, `end_date`, and `max_cloud_cover`;
- does not modify `state.plan`;
- updates `tool_calls[last_tool_index].params`;
- writes `runtime.adjustments` and `runtime.retry_counts`;
- sets `runtime.current_tool_index` back to the corresponding tool so the executor retries it.

The maximum retry count is 5.

### answer.generate_final_answer

`answer.generate_final_answer` usually executes as the final tool call.

- For the raster route, it generates the final answer from metadata produced by `metadata.export_metadata`.
- For the direct answer route, it answers general questions, system capability questions, or unsupported product requests directly.
- For unsupported products, it honestly explains that the product is not currently supported instead of forcing a mapping to an existing index.

### answer_node

`answer_node` is now mainly a safety fallback and terminal node:

- if `final_answer` already exists, return it directly;
- if the workflow failed before the answer tool, generate a failure response;
- if there is no final answer and the workflow has not failed, generate a fallback response.

## Tool Call Order

Compiler output for the `raster_product_generate` route:

```text
1. workspace.create_workspace
2. raster_prepare.prepare_raster_inputs
3. index_calculation.calculate_raster_index
4. render_preview.render_index_preview
5. metadata.export_metadata
6. answer.generate_final_answer
```

Compiler output for the `direct_answer` route:

```text
1. answer.generate_final_answer
```

## Output Directory

The final user-facing outputs are consistently named:

```text
data/
  <uuid>/
    output/
      metadata.json
      preview.png
      result.tif
```

Intermediate directories such as `aoi/`, `raster/`, `mosaic_raster/`, and `clipped_raster/` exist only during processing. `raster_prepare` deletes AOI, downloaded imagery, and mosaic intermediate directories; `index_calculation` deletes `clipped_raster/` after consuming clipped bands.
